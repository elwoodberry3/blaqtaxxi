# PRD — BLAQTAXXI

## 1. Problem

A solo driver is booking rides by DM: "hit me up an hour or two in advance." Every ride costs a chain of messages, the driver mentally tracks where he'll be after each drop-off, and the next rider can't tell where he is. The pricing is already simple ($20 flat; $25–$30 for long trips). The hard part is **scheduling around one physical car in real traffic**.

## 2. Users

| User | Job to be done |
|---|---|
| **Rider** | "Reserve my ride for Friday's interview, pay once, and know he's coming. When it's close, show me where he is." |
| **Driver** | "Show me my day. Only let people book what I can actually make. Keep my day full. Tell me early if I'm about to be late." |

## 3. Scope

### MVP (this course)
1. Rider booking: pickup, drop-off, date → **feasible time slots** → quote → pay → confirmation.
2. Rider ride page (signed link): countdown → T-30 live location + ETA → trip status → receipt.
3. Driver console: day timeline, status buttons, location drop, one-off time blocks, availability (default 05:00–24:00).
4. **Scheduling engine** (pure module): rush-hour-aware feasibility, dynamic slots, late-risk detection.
5. Flat-fee pricing tiers, Stripe **test-mode** payments, cancellation/no-show policy engine.
6. Async layer in n8n: confirmation, T-30 reminder, late notice, Slack digest.
7. Demo mode with zero credentials; TodoChips on every gap.

### V2 (documented, not built)
- Nudges: "Book 9:05 instead of 9:00 and it's guaranteed."
- Waitlist auto-fill when a slot opens.
- Tips, promo codes, repeat-rider shortcuts.
- Cash App / Zelle.
- Native app for true background location.

### Out of scope
- More than one driver / dispatch matching / surge pricing / ratings / in-app chat / airport-specific logic.

## 4. User stories and acceptance

| # | Story | Acceptance (testable) |
|---|---|---|
| U1 | As a rider, I see only times the driver can actually make | Slot list is generated by `findSlots()`; no slot violates the feasibility rule (property test) |
| U2 | As a rider, when the driver ends a ride near my pickup, I can book soon after | Given a ride ending Downtown, a Downtown pickup 15 min later is offered (SCHEDULER_SPEC case S3) |
| U3 | As a rider, a rush-hour 8 am trip doesn't let the driver double-book me | Lewisville → Downtown at 08:00 blocks a Lewisville pickup that would be reachable off-peak (case S2) |
| U4 | As a rider, I pay once and the price never changes | Quote locked at checkout; identical regardless of hour (case P3) |
| U5 | As a rider with a pickup tomorrow, I see a countdown, not a map | Ride page shows "in 32 h 10 m" until T-30 (UI test) |
| U6 | As a rider, 30 min before pickup I see where he is and how far | Location + ETA only inside window; before that the API returns `403 not_yet_visible` (API test) |
| U7 | As a driver, I see today's rides in order with gaps and drive times | Timeline renders from DB; gap minutes computed by engine |
| U8 | As a driver, I get warned when I'm going to be late for the next pickup | Ping that makes `projectedArrival > pickupAt` raises alert (case L1) |
| U9 | As a driver, I set availability once and it applies daily | Defaults to 05:00–24:00 America/Chicago; DST-day tests pass |
| U10 | As a driver, I can block off time | Block removes overlapping slots via the same feasibility rule |
| U11 | As either party, cancel/no-show follows a written policy | Policy table drives refund amounts (policy tests) |

## 5. Build-level success measures

These measure the **build**, not a business. No revenue, ride-count, or rating targets are claimed.

- Scheduler test suite covers every case in `SCHEDULER_SPEC.md` §8 and passes.
- App runs end to end in demo mode with zero credentials.
- One Playwright happy path: book → pay (test) → driver marks complete → receipt.
- Every unfinished item is visible as a TodoChip.
- Each phase yields episode notes and at least two 30–50 s clip candidates.

## 6. Risks (carry into the course as honest content)

| Risk | Impact | Mitigation |
|---|---|---|
| Iffy background location on iOS | Live ETA stalls if the driver locks the phone | Foreground pings + status-tap pings; UI shows "last seen N s ago" |
| Routing cost and accuracy | Bills add up; traffic predictions are estimates | Cache by grid cell + hour; buffer is a config; label estimates as estimates |
| Rush-hour under-estimation | Late pickups, angry riders | Peak multiplier and buffer tunable; late-risk alerts; calibrate from real trips post-launch |
| Regulatory, insurance, airport permits | Cannot legally launch | **Unverified.** See `COMPLIANCE_CHECKLIST.md`; gate for any real launch |
| SMS registration lead time | No texts at launch | Email + push fallback; SMS behind a seam |
| Payment fees at $20 tickets | Thin margin | Verify current Stripe pricing before any real launch; consider fee handling in policy |

## 7. One Build, Three Doors

- **Employment:** real-time scheduling engine + async layer + typed, tested domain core. Fits Applied AI / Automation / Agentic roles.
- **Consulting:** `lib/scheduler` generalizes to any solo operator who travels between appointments (mobile detailer, notary, groomer, barber). Reusable module.
- **Brand:** live-build series; the DM-to-app conversion is a story people already understand.
